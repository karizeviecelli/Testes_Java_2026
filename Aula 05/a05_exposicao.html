JUnit 5 · testes parametrizados
Aula 05 · 4 horas

Uma pergunta, muitos dados: testes parametrizados

Quando a regra é a mesma e apenas os valores mudam, não precisamos copiar o teste inteiro. O JUnit 5 executa o mesmo método várias vezes, uma vez para cada conjunto de dados.

Menos repetição

Um corpo de teste representa vários cenários.

Mais cobertura

Fica simples incluir valores comuns, extremos e fronteiras.

Falhas legíveis

Cada conjunto aparece como uma execução independente.

1 · Objetivos

O que você deverá conseguir fazer

Reconhecer repetição

Identificar testes que têm a mesma ação e asserção, mas usam dados diferentes.

Escolher a fonte

Usar @ValueSource, @CsvSource ou @MethodSource.

Mapear argumentos

Entender como cada dado chega aos parâmetros do método.

Testar limites

Incluir casos de fronteira e interpretar qual conjunto falhou.

Pré-requisito: reconhecer Arrange, Act e Assert e saber usar assertEquals e assertThrows.
2 · O problema

Três métodos repetem a mesma ideia

DescontoTest.java — antes
@Test
void descontoDe10PorCentoEm100() {
    assertEquals(90.0, Desconto.calcular(100.0, 10), 0.001);
}

@Test
void descontoDe20PorCentoEm200() {
    assertEquals(160.0, Desconto.calcular(200.0, 20), 0.001);
}

@Test
void descontoZeroMantemPreco() {
    assertEquals(80.0, Desconto.calcular(80.0, 0), 0.001);
}
O que muda?

Preço, percentual e resultado esperado.

O que não muda?

A chamada de calcular e a asserção.

Sinal de parametrização

Mesma regra + mesmos passos + dados diferentes.

3 · Modelo mental

Um método de teste, várias execuções

1. Fonte de dados

Entrega um valor ou conjunto de valores.

2. Parâmetros

Recebem os dados na mesma ordem e com tipos compatíveis.

3. Corpo do teste

Executa Arrange, Act e Assert para aquele caso.

4. Relatório

Mostra cada caso separadamente: um pode falhar e os demais passar.

Importante: três linhas em @CsvSource significam três execuções, embora exista somente um método Java.
4 · Preparação

Imports e dependência correta

Imports da classe de teste
import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.ValueSource;
import org.junit.jupiter.params.provider.CsvSource;
import org.junit.jupiter.params.provider.MethodSource;
import org.junit.jupiter.params.provider.Arguments;

import static org.junit.jupiter.api.Assertions.*;
Maven

Use org.junit.jupiter:junit-jupiter em escopo test. Esse artefato agrega o suporte aos parâmetros.

Erro comum

Importar org.junit.Test mistura JUnit 4 e JUnit 5. Aqui todos os imports começam com org.junit.jupiter.

5 · ValueSource

Um valor simples por execução

Percentuais válidos
@ParameterizedTest(name = "percentual {0}% deve ser aceito")
@ValueSource(ints = {0, 10, 50, 100})
void percentuaisValidosNaoDevemLancarExcecao(int percentual) {
    // Cada inteiro da lista chega aqui separadamente.
    assertDoesNotThrow(
        () -> Desconto.calcular(200.0, percentual)
    );
}
Execução 1

percentual = 0

Execução 2

percentual = 10

Execuções 3 e 4

50 e 100, incluindo as duas fronteiras.

Limite: @ValueSource fornece um único argumento por execução. Para entrada e resultado esperado, prefira @CsvSource.
6 · CsvSource

Vários argumentos na mesma linha

Preço, percentual e resultado esperado
@ParameterizedTest(name = "R$ {0} com {1}% = R$ {2}")
@CsvSource({
    "100.00, 10,  90.00",
    "200.00, 20, 160.00",
    " 80.00,  0,  80.00",
    " 50.00,100,   0.00"
})
void calcularDeveAplicarPercentual(
        double preco,
        int percentual,
        double esperado) {

    double obtido = Desconto.calcular(preco, percentual);

    assertEquals(esperado, obtido, 0.001);
}
Ordem

A 1ª coluna vai para preco; a 2ª, para percentual; a 3ª, para esperado.

Tipos

JUnit converte os textos do CSV para double e int.

Double

Use delta em assertEquals por causa da representação de ponto flutuante.

7 · Valores especiais

Textos com vírgula, nulos e vazios

RecursoQuando usarExemplo
@NullSourceExecutar uma vez com valor null.Validação de campos obrigatórios.
@EmptySourceExecutar com String, coleção ou array vazio."" em um nome obrigatório.
@NullAndEmptySourceCombinar os dois casos.Evitar dois testes quase iguais.
@CsvSource(delimiter=';')Quando os textos possuem vírgulas."Blumenau, SC;47"
Anotações de fonte podem ser combinadas. Porém, só combine quando todos os dados fizerem sentido para o mesmo corpo de teste.
8 · MethodSource

Dados complexos produzidos por um método

DescontoTest.java
@ParameterizedTest
@MethodSource("cenariosDeDesconto")
void calcularDeveAtenderCenarios(
        String descricao,
        double preco,
        int percentual,
        double esperado) {

    double obtido = Desconto.calcular(preco, percentual);
    assertEquals(esperado, obtido, 0.001, descricao);
}

static Stream<Arguments> cenariosDeDesconto() {
    return Stream.of(
        Arguments.of("sem desconto", 80.0, 0, 80.0),
        Arguments.of("desconto parcial", 200.0, 25, 150.0),
        Arguments.of("desconto total", 50.0, 100, 0.0)
    );
}
Por que static?

Por padrão, o JUnit chama a fonte sem criar uma instância da classe de teste.

Arguments.of

Agrupa todos os argumentos de uma execução.

Quando vale a pena?

Objetos, datas, listas, muitos casos ou dados construídos por código.

9 · Regra de produção

A classe testada precisa ser previsível

Desconto.java — código completo
package org.example;

public final class Desconto {
    // Classe utilitária: não deve ser instanciada.
    private Desconto() { }

    public static double calcular(double preco, int percentual) {
        if (preco < 0) {
            throw new IllegalArgumentException("O preço não pode ser negativo.");
        }
        if (percentual < 0 || percentual > 100) {
            throw new IllegalArgumentException(
                "O percentual deve estar entre 0 e 100."
            );
        }

        double valorDoDesconto = preco * percentual / 100.0;
        return preco - valorDoDesconto;
    }
}
Fronteiras válidas

Percentuais 0 e 100.

Logo fora das fronteiras

-1 e 101 devem lançar exceção.

Boa parametrização

Os dados contam a história completa da regra.

10 · Timeout

Um limite para o tempo de execução

Teste de tempo
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.Timeout;
import java.util.concurrent.TimeUnit;

@Test
@Timeout(value = 100, unit = TimeUnit.MILLISECONDS)
void calcularDeveTerminarRapidamente() {
    Desconto.calcular(250.0, 15);
}
O que comprova?

Que o método termina antes do limite estabelecido.

O que não comprova?

Não substitui um teste de carga ou benchmark.

Cuidado

Limites apertados podem falhar por lentidão do computador, não por defeito da regra.

11 · Escolha consciente

Qual fonte usar?

FonteDados por execuçãoMelhor uso
@ValueSourceUm valor simplesLista de números, textos, booleanos ou caracteres.
@CsvSourceVários valores simplesEntrada, regra e resultado esperado na própria anotação.
@MethodSourceValores simples ou objetosCenários complexos, reutilizáveis ou construídos por código.
@CsvFileSourceLinhas de arquivo CSVMuitos casos mantidos fora do código-fonte.
Regra prática: escolha a fonte mais simples que deixe os dados fáceis de ler e manter.
12 · Diagnóstico

Erros comuns e como corrigi-los

No ParameterResolver

Faltou uma fonte de dados ou a anotação usada não corresponde ao teste parametrizado.

ArgumentConversionException

O texto do CSV não pode ser convertido para o tipo do parâmetro.

PreconditionViolationException

O nome indicado em @MethodSource não existe ou não fornece dados.

Expected ≠ Actual

O caso foi executado, mas a regra ou o valor esperado está incorreto. Leia qual linha falhou.

13 · Fixação

Quiz rápido

1. Preciso fornecer preço, percentual e resultado esperado. Qual fonte é mais direta?

2. Quatro linhas em @CsvSource produzem quantas execuções?

3. Qual fonte aceita objetos construídos por código?

Fechamento

Parametrizar não é apenas “escrever menos”

É separar a regra do teste dos dados que exercitam a regra. Isso melhora a cobertura, evidencia fronteiras e facilita a inclusão de novos cenários.
