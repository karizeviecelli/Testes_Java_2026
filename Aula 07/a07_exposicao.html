Os atores contratados

Quando a Testemunha Real Não Pode Vir

Às vezes o tribunal contrata um ator para representar uma testemunha ausente. Um test double faz exatamente isso: substitui uma dependência real (banco, API, e-mail) por um "ator" controlado, para testarmos nosso código isoladamente.

O problema

Dependências externas em testes

public class NotificadorPedido {
    private ServicoEmail servicoEmail; // depende de algo externo!

    public void notificar(Pedido pedido) {
        servicoEmail.enviar(...); // enviaria um e-mail REAL no teste!
    }
}

Exemplo

Um Stub manual

public class ServicoEmailStub implements ServicoEmail {
    @Override
    public boolean enviar(String dest, String msg) {
        return true; // sempre "finge" que deu certo
    }
}
Exemplo

Um Fake manual

public class RepositorioClienteFake implements RepositorioCliente {
    private List<Cliente> clientes = new ArrayList<>();

    @Override
    public void salvar(Cliente c) { clientes.add(c); }
}

Implementação funcional de verdade, só que simplificada — "persiste" em memória, não em um banco real.

Diferença chave

Stub vs. Mock

STUB

  • Retorna respostas fixas e pré-definidas
  • Não verifica COMO foi chamado
  • "Eu só preciso de uma resposta controlada"

MOCK

  • Define comportamento esperado E verifica interações
  • Confirma se um método foi chamado, quantas vezes, com quais argumentos
  • "Eu quero PROVAR que a interação aconteceu"

2. Por que não testamos NotificadorPedido usando o ServicoEmail real?

Porque enviaria e-mails reais a cada execução do teste — lento e indesejável
Porque o JUnit bloqueia chamadas de rede automaticamente
