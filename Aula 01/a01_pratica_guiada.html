Prática guiada — classe ContaBancaria

Siga os passos abaixo, na ordem, replicando o raciocínio de construção de uma classe de entidade bem encapsulada.

1
Declarar a classe e os atributos privados
▶

Crie a classe ContaBancaria com três atributos privados: titular (String), numeroConta (String) e saldo (double).

public class ContaBancaria {
    private String titular;
    private String numeroConta;
    private double saldo;
}
Por que private? Porque ninguém fora da classe deve poder alterar o saldo diretamente — isso é a base do encapsulamento.
2
Criar o construtor (saldo sempre inicia em 0.0)
▶

O construtor recebe titular e numeroConta, e sempre inicia o saldo em 0.0 — nunca deixe isso a cargo de quem usa a classe.

public ContaBancaria(String titular, String numeroConta) {
    this.titular = titular;
    this.numeroConta = numeroConta;
    this.saldo = 0.0;
}
Um construtor bem feito nunca deixa o objeto "pela metade". Toda ContaBancaria já nasce pronta para uso.
3
Implementar depositar(double valor)
▶

Deve somar o valor ao saldo, mas lançar IllegalArgumentException se o valor for menor ou igual a zero.

public void depositar(double valor) {
    if (valor <= 0) {
        throw new IllegalArgumentException("O valor do depósito deve ser maior que zero.");
    }
    this.saldo += valor;
}
Essa validação é exatamente o tipo de "regra do tribunal" que vamos formalizar como teste em breve: "o que acontece se o valor for zero ou negativo?"
4
Implementar sacar(double valor)
▶

Deve subtrair o valor do saldo, mas lançar IllegalArgumentException se o valor for maior que o saldo disponível (ou ≤ 0).

public void sacar(double valor) {
    if (valor <= 0) {
        throw new IllegalArgumentException("O valor do saque deve ser maior que zero.");
    }
    if (valor > this.saldo) {
        throw new IllegalArgumentException("Saldo insuficiente para este saque.");
    }
    this.saldo -= valor;
}
Repare que temos duas regras diferentes aqui — isso significa, no futuro, dois casos de teste distintos para o método sacar().
5
Getters e reflexão final
▶

Implemente os getters (sem setSaldo()!) e responda: por que essa classe está pronta para ser bem testada?

public String getTitular() { return titular; }
public String getNumeroConta() { return numeroConta; }
public double getSaldo() { return saldo; }
// Sem setSaldo(): o saldo só muda via depositar() e sacar()
Porque cada regra de negócio está isolada em um método com nome claro — isso significa um caso de teste natural para cada uma delas.
